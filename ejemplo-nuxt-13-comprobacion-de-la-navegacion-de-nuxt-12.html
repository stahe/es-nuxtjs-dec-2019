    16. Ejemplo [nuxt-13]: Comprobación de la navegación de [nuxt-12]

    En este ejemplo, nos centramos en la navegación de [nuxt-12]. No lo hicimos en [nuxt-12] porque controlar la navegación habría añadido complejidad a un ejemplo que ya era complejo.

    Objetivo: queremos que el usuario solo pueda realizar acciones autorizadas:

    • si la sesión JSON no ha comenzado, solo se permite la URL [/];
    • si la sesión JSON ha comenzado pero el usuario no está autenticado, solo se permite la URL [/authentication];
    • si la sesión JSON ha comenzado y el usuario está autenticado, solo se permiten las URL [/get-admindata, /end-session];
    • cuando el destino de enrutamiento actual no esté autorizado, se realizará una redirección a una URL autorizada;

    Los cambios se realizarán en la carpeta de enrutamiento [middleware].

    16.1. Enrutamiento para la aplicación [nuxt]

    El enrutamiento de la aplicación se configura de la siguiente manera en el archivo [nuxt.config]:

    
// router
  router: {
    // application URL root
    base: '/nuxt-13/',
    // routing middleware
    middleware: ['routing']
},
    • línea 6: el enrutamiento de la aplicación se controla mediante el archivo [middleware/routing];

    El archivo [middleware/routing] es el siguiente:

    
/* eslint-disable no-console */
 
// on importe les middleware du serveur et du client
import serverRouting from './server/routing'
import clientRouting from './client/routing'
 
export default function(context) {
  // qui exécute ce code ?
  console.log('[middleware], process.server', process.server, ', process.client=', process.client)
  if (process.server) {
    // routage serveur
    serverRouting(context)
  } else {
    // routage client
    clientRouting(context)
  }
}
    • líneas 10–16: el enrutamiento del cliente y del servidor [nuxt] se gestiona de forma diferente. Este es un punto de diferencia importante entre ambos;
    • línea 4: el enrutamiento del servidor se implementa mediante el script [middleware/server/routing];
    • línea 5: el enrutamiento del cliente se implementa mediante el script [middleware/client/routing];

    • línea 4: la opción [Authentication] solo está disponible si la sesión JSON ha comenzado pero el usuario no está autenticado. Si la sesión JSON no ha comenzado o el usuario ya está autenticado, la opción no está disponible;
    • Líneas 7-11: la opción [Solicitud de datos de administración] solo está disponible si la sesión JSON ha comenzado, el usuario está autenticado y los datos de administración aún no se han recuperado. Si no se cumple alguna de estas tres condiciones (sesión JSON no iniciada, usuario no autenticado o datos de administración ya recuperados), la opción no se ofrece;
    • Línea 15: la opción [End Tax Session] está disponible tan pronto como se haya iniciado la sesión JSON y el usuario esté autenticado; de lo contrario, no está disponible;

    16.3. Enrutamiento del servidor [Nuxt]

    El enrutamiento del servidor suele ser más complejo que el enrutamiento del lado del cliente, ya que el usuario puede escribir cualquier URL en la barra de direcciones de su navegador. Podemos permitir que eso ocurra (al fin y al cabo, no se supone que el usuario haga eso) o intentar controlarlo. Eso es lo que haremos aquí, a efectos de este ejemplo, porque en el caso de la aplicación [nuxt-12], podemos prescindir fácilmente de ello, ya que el servidor de cálculo de impuestos está bien protegido contra estas URL introducidas manualmente y sabe cómo enviar los mensajes de error adecuados. Lo vimos en [next-12], donde no había control de enrutamiento.

    El enrutamiento en un servidor [nuxt] es muy diferente al de un cliente [nuxt] en lo que respecta a la redirección:

    • cuando un servidor [nuxt] es redirigido, envía una solicitud de redirección al navegador del cliente con el destino de la redirección. A continuación, el navegador realiza una nueva solicitud al servidor [nuxt], pidiendo el destino que se le ha enviado. Es como si el usuario hubiera escrito manualmente la URL del destino de la redirección: toda la aplicación [nuxt] se reinicia y, con ella, todo su ciclo de vida (plugins del servidor, store, enrutamiento del servidor, páginas);
    • cuando se redirige un cliente [nuxt], nada de esto ocurre. Simplemente se produce un cambio de página, igual que habría ocurrido si el usuario hubiera hecho clic en un enlace que llevara al destino de la redirección. El ciclo de vida es entonces diferente (enrutamiento del lado del cliente, renderización del destino de la ruta);

    Por este motivo, es preferible separar el enrutamiento del lado del cliente del enrutamiento del lado del servidor, aunque las dos bases de código puedan parecer similares.

    El script de enrutamiento del servidor [middleware/server/routing] será el siguiente:

    
/* eslint-disable no-console */
export default function(context) {
  // qui exécute ce code ?
  console.log('[middleware server], process.server', process.server, ', process.client=', process.client)
 
  // on récupère quelques informations dans le store [nuxt]
  const store = context.store
  // d'où vient-on ?
  const from = store.state.from || 'nowhere'
  ...
}
    • En el enrutamiento del lado del cliente, la función de enrutamiento recibe el contexto [context] con la propiedad [context.from], que es la ruta de la página de la que venimos. La ruta a la que nos dirigimos se obtiene a través de [context.route];
    • En el enrutamiento del lado del servidor, la función de enrutamiento recibe el contexto [context] sin la propiedad [context.from]. El enrutamiento del lado del servidor solo se produce cuando se solicita manualmente una URL al servidor [nuxt]. Sabemos que, en ese momento, toda la aplicación [nuxt] se reinicia. Es como si empezáramos desde cero, por lo que no existe el concepto de «página anterior»;
    • gracias a la sesión [nuxt], sabemos que el servidor puede recuperar esta sesión y así evitar empezar desde cero. Por lo tanto, es en esta sesión [nuxt], y más concretamente en el almacén de la sesión, donde almacenaremos el nombre de la última página mostrada por el navegador del cliente antes de que se solicite una URL al servidor [nuxt];
    • Líneas 7–9: Recuperamos el nombre de la última página mostrada por el navegador del cliente. Cuando se inicia la aplicación, esta información [from] no existe en el almacén. A continuación, asignamos el nombre [nowhere] a la variable [from];

    Para que el servidor [nuxt] pueda recuperar del almacén el nombre de la última página mostrada por el navegador del cliente, el cliente [nuxt] también debe introducir esta información en el almacén. Por lo tanto, el script de enrutamiento del cliente [nuxt] queda completado de la siguiente manera:

    
/* eslint-disable no-console */
export default function(context) {
  // qui exécute ce code ?
  console.log('[middleware client], process.server', process.server, ', process.client=', process.client)
  // gestion du cookie de la session PHP dans le navigateur
  // le cookie de la session PHP du navigateur doit être identique à celui trouvé en session nuxt
  // l'acion [fin-session] reçoit un nouveau cookie PHP (serveur comme client nuxt)
  // si c'est le serveur qui le reçoit, le client doit le transmettre au navigateur
  // pour ses propres échanges avec le serveur PHP
  // on est ici dans un routing client
 
  // on récupère le cookie de la session PHP
  const phpSessionCookie = context.store.state.phpSessionCookie
  if (phpSessionCookie) {
    // s'il existe, on affecte le cookie de session PHP au navigateur
    document.cookie = phpSessionCookie
  }
 
  // on met dans la session le nom de la page où on va - pas de redirection serveur
  context.store.commit('replace', { serverRedirection: false, from: context.route.name })
  // on sauvegarde le store dans la session [nuxt]
  const session = context.app.$session()
  session.value.store = context.store.state
  session.save(context)
}
    • Se añaden las líneas 19–24;
    • Línea 20: Almacenamos el nombre de la página [context.route.name] que se mostrará en el almacén, que luego servirá como la página de la que venimos durante el siguiente paso de enrutamiento. Además, veremos que, en el enrutamiento del servidor [nuxt], este necesita saber si el enrutamiento actual proviene de una redirección previa realizada por el servidor [nuxt]. En este caso, no es así, por lo que establecemos la propiedad [serverRedirection] en [false];
    • líneas 22–24: el estado del almacén se coloca en la sesión [nuxt] (línea 23), luego la sesión [nuxt] se guarda en una cookie (línea 24), que a su vez se guardará en el navegador del cliente [nuxt];

    Volvamos al script de enrutamiento del servidor [nuxt]:

    
/* eslint-disable no-console */
export default function(context) {
  // qui exécute ce code ?
  console.log('[middleware server], process.server', process.server, ', process.client=', process.client)
 
  // on récupère quelques informations dans le store [nuxt]
  const store = context.store
  // d'où vient-on ?
  const from = store.state.from || 'nowhere'
  // où va-t-on ?
  const to = context.route.name
  // éventuelle redirection
  let redirection = ''
  // gestion du routage terminé
  let done = false
 
  // est-on déjà dans une redirection du serveur [nuxt]?
  if (store.state.serverRedirection) {
    // rien à faire
    done = true
  }
 
  // est-ce un rechargement de page ?
  if (to === from) {
    // rien à faire
    done = true
  }
 
  // contrôle de la navigation du serveur [nuxt]
  // on s'inspire de la navigation client dans le composant [navigation]
 
  // cas où la session PHP n'a pas démarré
  if (!done && !store.state.jsonSessionStarted && to !== 'index') {
    // redirection
    redirection = 'index'
    // travail terminé
    done = true
  }
 
  // cas où l'utilisateur n'est pas authentifié
  if (!done && store.state.jsonSessionStarted && !store.state.userAuthenticated && to !== 'authentification') {
    // redirection
    redirection = from
    // travail terminé
    done = true
  }
 
  // cas où l'utilisateur a été authentifié
  if (!done && store.state.jsonSessionStarted && store.state.userAuthenticated && to !== 'get-admindata' && to !== 'fin-session') {
    // on reste sur la même page
    redirection = from
    // travail terminé
    done = true
  }
 
  // cas où [adminData] a été obtenu
  if (!done && store.state.jsonSessionStarted && store.state.userAuthenticated && store.state.adminData && to !== 'fin-session') {
    // on reste sur la même page
    redirection = from
    // travail terminé
    done = true
  }
 
  // on a fait tous les contrôles ---------------------
  // redirection ?
  if (redirection) {
    // on note la redirection dans le store
    store.commit('replace', { serverRedirection: true })
  } else {
    // pas de redirection
    store.commit('replace', { serverRedirection: false, from: to })
  }
  // on sauvegarde le store dans la session [nuxt]
  const session = context.app.$session()
  session.value.store = store.state
  session.save(context)
  // on fait l'éventuelle redirection
  if (redirection) {
    context.redirect({ name: redirection })
  }
}
    • líneas 6–9: recuperamos el valor de [from] del almacén del servidor [nuxt];
    • línea 11: anotamos el destino de la ruta actual;
    • línea 13: el enrutamiento puede dar lugar a una redirección del navegador del cliente. [redirection] será el destino de esta redirección;
    • línea 15: [done] establecido en [true] indica que el enrutamiento ha finalizado;
    • líneas 17–21: En primer lugar, comprobamos si el enrutamiento actual se debe a una solicitud de redireccionamiento enviada al navegador del cliente. Esta información se almacena en la propiedad [serverRedirection] del almacén. Si esta propiedad es true, entonces el servidor [nuxt] envió un redireccionamiento al navegador del cliente durante la solicitud anterior al servidor [nuxt]. En este caso, no es necesario realizar ningún enrutamiento. Durante la solicitud anterior, el enrutador del servidor [nuxt] decidió que el navegador del cliente debía ser redirigido. No es necesario anular esta decisión con un nuevo enrutamiento;
    • líneas 23–27: comprobamos si el enrutamiento actual es una recarga de página. Si es así, dejamos que continúe;
    • A partir de la línea 29, retomamos las reglas aplicadas en el componente [navigation] del cliente [nuxt] (véase el párrafo anterior);
    • líneas 32–38: gestionamos el caso en el que la sesión JSON no ha comenzado y el destino de la ruta no es la página [index]. En este caso, redirigimos el navegador del cliente a la página [index];
    • líneas 40–46: gestionamos el caso en el que la sesión JSON ha comenzado, el usuario no está autenticado y el destino de enrutamiento actual no es la página [authentication]. En este caso, rechazamos el enrutamiento y permanecemos donde estábamos;
    • líneas 48–54: gestionan el caso en el que la sesión JSON ha comenzado, el usuario está autenticado y el destino de enrutamiento actual no es ni la página [get-admindata] ni la página [end-session], que son entonces los únicos destinos posibles. En este caso, se rechaza el enrutamiento solicitado y volvemos a donde estábamos anteriormente;
    • líneas 56–62: gestionamos el caso en el que se ha obtenido [adminData]. En este caso, solo hay un destino de enrutamiento posible: la página [fin-session]. Si esa no era la página solicitada, rechazamos el enrutamiento y volvemos a donde estábamos anteriormente;
    • líneas 64–72: si se ha producido una redirección, la registramos en el almacén del servidor [nuxt]: [serverRedirection: true]. Ten en cuenta que no asignamos ningún valor a la propiedad [from] del almacén. El motivo es que habrá una redirección desde el navegador del cliente, y hemos visto que, en este caso, no hubo enrutamiento (líneas 17–20) y la propiedad [from] del almacén no se utiliza;
    • Líneas 66–69: Si no hay redireccionamiento, esto también se anota en el almacén del servidor [nuxt]: [serverRedirection: false]. Además, el enrutamiento actual mostrará la página [to], que para la siguiente solicitud (del cliente o del servidor [nuxt]) se convertirá en la página anterior. Por eso escribimos [from: to];
    • líneas 73–76: Guardamos el almacén en la sesión [nuxt], que a su vez se guarda en una cookie;
    • líneas 77–80: si [redirection] no está vacío, entonces le indicamos al navegador que redirija. De lo contrario (no se muestra aquí), el ciclo de vida del servidor [nuxt] continuará: la página [to] será procesada por el servidor [nuxt] y enviada al navegador del cliente [nuxt] junto con la cookie de sesión [nuxt];

    El enrutamiento elegido aquí para el servidor [nuxt] es arbitrario. Podríamos haber elegido otro o, como se ha mencionado, no haber utilizado ningún enrutamiento. El elegido anteriormente tiene la ventaja de mantener siempre la aplicación en un estado estable, independientemente de la URL solicitada por el usuario.

    Podemos mejorar esto ligeramente cuando la página que se carga finalmente es la página original. Hay dos casos:

    • el usuario ha provocado una recarga de la página (to===from);
    • hay redireccionamientos a la página original (redirección===desde);

    En ambos casos, la página original se ejecutará de nuevo con su llamada asíncrona al servidor de cálculo de impuestos. Veamos un ejemplo. La página [to=authentication] será ejecutada por el servidor [nuxt]. Si no hacemos nada, la función [asyncData] se ejecutará de nuevo. Esto es innecesario, ya que la autenticación ya se ha realizado.

    16.5. Conclusión

    El enrutamiento en el servidor [nuxt] es complejo porque debes anticipar todas las URL que el usuario podría escribir manualmente. Este es un ejemplo clásico. Una aplicación [nuxt] no está pensada para usarse de esta manera. Una vez que la página [index] es servida por el enrutador del servidor [nuxt], las solicitudes posteriores realizadas al servidor podrían ser redirigidas a una página de error.

    En el caso concreto de nuestro ejemplo [nuxt-13], el enrutamiento del servidor [nuxt] era innecesario. El comportamiento predeterminado (esencialmente, sin enrutamiento) del ejemplo [nuxt-12] funcionaba perfectamente.
