    4. Ejemplo [nuxt-01]: Enrutamiento y navegación

    Crearemos una serie de ejemplos sencillos para descubrir poco a poco cómo funciona una aplicación [nuxt]. Comenzaremos portando la aplicación [vuejs-11] del documento |Introducción al marco VUE.JS a través de ejemplos|, para descubrir en primer lugar qué diferencia la organización del código de una aplicación [nuxt] de la de una aplicación [vue].

    4.1. Estructura del directorio del proyecto

    El proyecto [vuejs-11] era un proyecto que implicaba la navegación entre vistas:

    La estructura de directorios del código fuente del proyecto [vuejs-11] era la siguiente:

    • [main.js] era el script que se ejecutaba al iniciar la aplicación [vue];
    • [router.js] definía las reglas de enrutamiento;
    • [App.vue] era la vista de estructuración de la aplicación. Organizaba el diseño de las diferentes vistas;
    • [Componente1, Componente2, Componente3, Diseño, Navegación] eran los componentes utilizados en las distintas vistas de la aplicación;

    Al portar la aplicación [Vue] [1] a una aplicación [Nuxt] [2]:

    • los scripts que se ejecutan al iniciar la aplicación deben declararse en la clave [plugins] del archivo [nuxt.config.js]. Además, es posible separar los scripts destinados al servidor [nuxt] de los destinados al cliente [nuxt];
    • la vista [App.vue] debe colocarse en la carpeta [layouts] y renombrarse como [default.vue];
    • los componentes [Component1, Component2, Component3], que son los destinos de enrutamiento, deben moverse a la carpeta [pages]. Uno de ellos, el que sirve como página de inicio, debe renombrarse como [index.vue]. Aquí, hemos renombrado los archivos:
      • [Component1] --> [index]: muestra el texto [Inicio];
      • [Component2] --> [page1]: muestra el texto [Página 1];
      • [Component3] --> [page2]: muestra el texto [Página 2];

    [nuxt] utiliza el contenido de la carpeta [pages] para generar dinámicamente las siguientes rutas:

    1
2
3
    { name :’index’, ‘path’ :’/’}
{ name :’page1’, ‘path’ :’/page1’}
{ name :’page2’, ‘path’ :’/page2’}

    Como resultado, el archivo [router.js] utilizado en el proyecto [vue] deja de ser necesario en el proyecto [nuxt].

    4.2. Portar el archivo [main.js]

    El archivo [main.js] del proyecto [vuejs-11] era el siguiente:

    
// imports
import Vue from 'vue'
import App from './App.vue'
 
// plugins
import BootstrapVue from 'bootstrap-vue'
Vue.use(BootstrapVue);
 
// bootstrap
import 'bootstrap/dist/css/bootstrap.css'
import 'bootstrap-vue/dist/bootstrap-vue.css'
 
// routeur
import monRouteur from './router'
 
// configuration
Vue.config.productionTip = false
 
// instanciation projet [App]
new Vue({
  name: "app",
  // vue principale
  render: h => h(App),
  // routeur
  router: monRouteur,
}).$mount('#app')

    Aparte de las [importaciones], el código hace lo siguiente:

    • líneas 5–11: utiliza la biblioteca [bootstrap-vue]. Esto ahora lo gestiona el módulo [bootstrap-vue/nuxt] en la línea 43 del archivo de configuración [nuxt.config.js];
    • líneas 14 y 25: uso del archivo de enrutamiento [router.js]. Ahora la aplicación [nuxt] lo hace automáticamente basándose en la estructura de directorios de la carpeta [pages];
    • líneas 20–26: instanciación de la vista principal de la aplicación. En una aplicación [nuxt], la vista [layouts/default.vue] sirve como vista principal;

    El archivo [main.js] ya no es necesario. Si lo hubiera sido, lo habríamos declarado en la clave [plugins] en la línea 30 del archivo de configuración [nuxt.config.js];

      </b-alert>

<script>
export default {
  name: 'App'

    • En la línea 9, en el proyecto [vuejs-11], teníamos la etiqueta <router-view /> en lugar de la etiqueta <nuxt /> que se utiliza aquí. Ambas parecen funcionar. Probé las dos sin observar ningún cambio. Mantuve la etiqueta <nuxt />, que es la recomendada. Muestra la vista actual, es decir, la página de destino de la ruta actual;

    Este componente muestra tres enlaces de navegación:

    Para determinar qué valores asignar a los atributos [to] de las líneas 4, 7 y 10, consulta la carpeta [pages] [2]:

    • la página [index] tendrá la URL [/] ;
    • la página [page1] tendrá la URL [/page1];
    • la página [page2] tendrá la URL [/page2];

    El componente [navigation] también se puede escribir de la siguiente manera:

    
<template>
  <!-- bootstrap menu with three options -->
  <b-nav vertical>
    <nuxt-link to="/" exact exact-active-class="active">
      Home
    </nuxt-link>
    <nuxt-link to="/page1" exact exact-active-class="active">
      Page 1
    </nuxt-link>
    <nuxt-link to="/page2" exact exact-active-class="active">
      Page 2
    </nuxt-link>
  </b-nav>
</template>

    La etiqueta <b-nav-item> se sustituye por la etiqueta <nuxt-link>, que denota un enlace de enrutamiento. En la práctica, no noté ninguna diferencia significativa, nada que inclinara la balanza a favor de una etiqueta sobre la otra.

    4.5. Las páginas

    La página [index.vue] muestra la siguiente vista:

    El código de la página es el siguiente:

    
<!-- page principale -->
<template>
  <Layout :left="true" :right="true">
    <!-- navigation -->
    <Navigation slot="left" />
    <!-- message-->
    <b-alert slot="right" show variant="warning">
      Home
    </b-alert>
  </Layout>
</template>
 
<script>
/* eslint-disable no-undef */
/* eslint-disable no-console */
/* eslint-disable nuxt/no-env-in-hooks */
 
import Navigation from '@/components/navigation'
import Layout from '@/components/layout'
 
export default {
  name: 'Home',
  // components used
  components: {
    Layout,
    Navigation
  },
  // life cycle
  beforeCreate(...args) {
    console.log('[home beforeCreate]', 'process.server=', process.server,
 'process.client=', process.client, "nombre d'arguments=", args.length)
  },
  created(...args) {
    console.log('[home created]', 'process.server=', process.server,
 'process.client=', process.client, "nombre d'arguments=", args.length)
  },
  beforeMount(...args) {
    console.log('[home beforeMount]', 'process.server=', process.server,
 'process.client=', process.client, "nombre d'arguments=", args.length)
  },
  mounted(...args) {
    console.log('[home mounted]', 'process.server=', process.server,
 'process.client=', process.client, "nombre d'arguments=", args.length)
  }
}
</script>
    • línea 5: el componente de navegación se coloca en la columna izquierda;
    • líneas 7–9: se coloca una alerta en la columna derecha;

    En la sección <script>, colocamos código en las funciones del ciclo de vida de la página [beforeCreate, created, beforeMount, beforeMounted]. Queremos saber cuáles son ejecutadas por el servidor []nuxt y cuáles por el cliente [nuxt]. Recordemos dos cosas:

    • cuando se solicita una página —ya sea al iniciar la aplicación (como con la página [index]) o manualmente por parte del usuario al actualizar la página del navegador o escribir una URL a mano—, primero la entrega el servidor [nuxt]. El servidor interpreta el código anterior y ejecuta el JavaScript que contiene;
    • cuando la página enviada por el servidor [nuxt] llega al navegador, lo hace con el código del lado del cliente [nuxt]. A continuación, el código del lado del cliente vuelve a ejecutar el código anterior;
    • Utilizamos registros para rastrear quién está haciendo qué con el fin de comprender mejor este proceso;
    • Líneas 30–31: Utilizamos un objeto global [process] en la función que existe tanto en el servidor como en el cliente:
      • [process.server] es verdadero si el código es ejecutado por el servidor, falso en caso contrario;
      • [process.client] es verdadero si el código es ejecutado por el cliente, falso en caso contrario;
      • Dado que la variable [process] no está declarada en el código, debemos incluir la línea 14 para [eslint]. La línea 16 es necesaria porque, de lo contrario, [eslint] informa de un tipo diferente de error debido a la variable [process]. La línea 15 es necesaria para permitir el uso de [console] en las funciones del ciclo de vida;
    • línea 29: también queremos saber si las funciones del ciclo de vida reciben argumentos. De hecho, descubriremos que [nuxt] pasa información a ciertas funciones. Queremos saber si las funciones del ciclo de vida se encuentran entre ellas;
    • Repetimos el mismo código para las cuatro funciones;

    4.7. Ejecución del proyecto

    Ejecutamos el proyecto:

    La página que se muestra es la siguiente:

    Una vez cargada en el navegador, la aplicación [nuxt] se convierte en una aplicación [vue] estándar. Por lo tanto, no trataremos el comportamiento del lado del cliente de la aplicación [nuxt-01]. Esto ya se trató en el proyecto [vuejs-11] del documento |Introducción al marco VUE.JS a través de ejemplos|.

    La aplicación [nuxt] se diferencia de la aplicación [vue] solo en dos aspectos:

    • el inicio inicial de la aplicación, que muestra la página de inicio;
    • cada vez que el usuario actualiza el navegador de cualquier forma;

    En ambos casos:

    • el servidor envía la página solicitada;
    • la página recibida es procesada por el cliente;

    Echemos un vistazo a los registros de inicio de la aplicación (F12 en el navegador):

    • en [1], los registros del servidor (process.server=true). Aparecen precedidos por la etiqueta [Nuxt SSR] (SSR = renderizado del lado del servidor);
    • en [2], los registros del cliente en el navegador (process.client=true);

    A partir de estos registros, podemos deducir que:

    • el servidor ejecuta las funciones del ciclo de vida [beforeCreate, created];
    • el cliente ejecuta las funciones del ciclo de vida [beforeCreate, created, beforeMount, mounted];
    • el servidor procesó la página antes que el cliente;
    • en ambos casos, ninguna de las funciones ejecutadas recibe argumentos;

    Líneas 33, 37 y 42: los enlaces son problemáticos. Parecen enlaces normales que, al hacer clic en ellos, envían una solicitud al servidor. Sin embargo, al ejecutarlos, vemos que no es así: no se envía ninguna solicitud al servidor. Para entender por qué, tenemos que volver a la pestaña [Inspector] del navegador:

    Vemos que en [1, 2] se han asociado eventos a los enlaces. Son los scripts de las líneas 71–74 los que han asociado los controladores de eventos a los enlaces. Por lo tanto:

    • la página mostrada por el cliente es visualmente idéntica a la enviada por el servidor;
    • el cliente ha añadido comportamiento dinámico a la página;

    Obtenemos el mismo tipo de página que la página [index], pero con la alerta de vista [Página 1] (línea 30). Líneas 41-44: el código del lado del cliente se ha enviado junto con la página. En definitiva, solicitar manualmente una URL equivale a reiniciar la aplicación. La única diferencia es que la página que se muestra no es necesariamente la página de inicio, sino la que se ha solicitado. Una vez recibida la página, el cliente toma el control. Ya no se contactará con el servidor a menos que el usuario decida lo contrario.
